# ADR-0013: VFS and file systems

- Status: Accepted
- Date: 2026-10-19

## Context

Phase 5 brings persistent storage: a VFS whose vnodes change, the name cache, mounting, caching and
write-back, and four file systems (tmpfs, devfs, UFS2, msdosfs). The P4 VFS serves only file
systems built once and never changed. Like the driver model, the VFS is hard to change once file
systems depend on it, and two of its properties are exit criteria: images must pass FreeBSD's
`fsck`, and the P5 benchmarks must be within 2% of FreeBSD
([ADR-0011](0011-performance-parity.md)).

FreeBSD's VFS defines what userland sees (`stat`, `statfs`, `getdirentries`, `nmount`, `errno`s)
and what is on disk. Its internals carry history: VOPs dispatched through untyped tables,
`v_usecount` and `v_holdcnt` managed by hand, and lock-order rules enforced only at run time.

## Decision

Adopt the design in [VFS.md](../VFS.md). Its load-bearing parts:

1. **FreeBSD's userland view and on-disk formats exactly**, checked by abi-check, by differential
   tests against FreeBSD, and by FreeBSD's `fsck_ffs` and `fsck_msdosfs` on images AbyssBSD wrote.
2. **Memory and use references are different types**: `Arc<Vnode>` for memory, a `VnodeUse` guard
   for opens, working directories, and mappings. Dropping the last use runs `inactive`.
3. **One vnode per inode**, through a per-mount table of weak references. Unused vnodes are kept on
   an LRU and reclaimed past `kern.maxvnodes`.
4. **The generic layer owns the protocol**: locking order, name-cache maintenance, `..`, mount
   crossing, permission checks, and timestamps. File systems implement typed operations on locked
   vnodes.
5. **One page cache for file data**: the vnode's VM object, shared by `read`, `write`, and `mmap`,
   with dirty tracking by write fault. Metadata goes through a separate buffer cache, which soft
   updates hangs dependencies on.
6. **On-disk engines in pure `lib/` crates** (`lib/ufs`, `lib/fat`) over a block-device trait,
   host-tested against images made and checked by FreeBSD's tools on the build server.
7. **Cross-directory renames serialize per mount** on a rename lock, instead of FreeBSD's
   lock-and-retry.
8. **A path to lockless lookup** (one read-side section per walk, one reference taken at the end),
   built when the name-cache benchmarks need it.

## Consequences

- File systems are smaller: they never reimplement lookup rules or cache maintenance.
- The `lib/` engines can be exercised by fuzzers and random workloads on the host, with FreeBSD's
  `fsck` as the oracle.
- Serializing cross-directory renames per mount costs concurrency that no P5 benchmark measures.
  It is revisited if a later workload shows it.
- FreeBSD's `fsx` is under the APSL. It is built from the FreeBSD tree on the build server and run
  as a test program, never copied into this repository.
